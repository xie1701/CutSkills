# 术语表

给用户解释时先查这里。面向用户的默认规则：**每个专有词第一次出现时，跟一句「它是什么、为什么跟你有关」**，不要只写英文缩写。

## 视频规格

| 术语 | 一句话释义 | 在 CutSkills 里意味着什么 |
|---|---|---|
| **分辨率 / 4K / 1080p** | 画面的像素数，4K 是 3840×2160，1080p 是 1920×1080。像素越多越清晰，也越吃算力 | 4K 素材做代理（proxy）能省一半以上解码时间 |
| **帧率 / fps** | 每秒多少帧画面。29.97、59.94 这类非整数帧率来自 NTSC 电视体系 | 非整数帧率按秒切点会累积漂移，长片要按帧对齐 |
| **VFR / CFR** | 可变帧率 / 固定帧率。手机在暗光或省电时会动态掉帧，就成了 VFR（可变帧率） | VFR 素材转成 CFR 再剪，否则切点会撞出重复帧 |
| **码率 / bitrate** | 每秒用多少数据存画面，决定画质与文件大小 | 单文件 >1GB 的标 `huge`，适合进冷存储 |
| **编码 / codec / HEVC / H.265** | 压缩画面的算法。HEVC（H.265）比 H.264 同画质省一半体积，但解码更吃硬件 | iPhone 默认 HEVC；交付给 Windows/安卓要先确认能播 |
| **ProRes** | 苹果的剪辑用编码，体积大、几乎不压缩、剪起来最顺 | 素材是 HEVC 时，中间渲染用 ProRes 或 H.264 高质量更稳 |
| **pix_fmt / 色深 / 8bit / 10bit** | 每个像素用多少位存颜色。10bit 有 1024 级亮度，渐变更不容易出现色带 | 10bit 素材转 8bit 时渐变会起「梯田」，要加抖动 |
| **色域 / BT.709 / BT.2020** | 能表示多少种颜色。BT.709 是高清标准，BT.2020 是超高清广色域 | 广色域转 709 饱和度会掉，品牌色要重新取值 |
| **SDR / HDR / HLG / PQ** | 标准动态 vs 高动态。HLG（混合对数伽马）和 PQ（感知量化）是两种 HDR 曲线，PQ 常见于 HDR10，HLG 常见于手机和广播 | 混剪必须统一：HDR 转 SDR（tone mapping），否则一段灰一段正常 |
| **杜比视界 / Dolby Vision** | HDR 的加强版：除了基础画面，还有逐帧的动态元数据。iPhone 录的常见 Profile 8.4，基底是 HLG | 普通工具只认基础层，剪完颜色会漂；先转 SDR 代理再剪 |
| **tone mapping** | 把 HDR 映射到 SDR 的算法，决定「高光压多少、暗部提多少」 | 不做会发灰发白；做过头会死黑 |
| **rotation / 旋转元数据** | 手机竖拍时像素仍横着存，靠元数据里的 90° 标记显示成竖屏 | 按像素宽高判横竖会全判反；`-c copy` 或部分滤镜会丢旋转 |
| **GOP / 关键帧** | 视频不是每帧都完整存，关键帧（I 帧）之后是增量帧。GOP 越长，随机定位越慢 | 切点要落在关键帧附近更省时间，精确切点要靠重编码 |
| **代理 / proxy** | 用低分辨率副本代替原片剪辑，最后输出时再换回原片 | 4K HEVC 库必做，索引里该有代理路径 |
| **抽帧 / contact sheet / 联系表** | 从一段视频里等间隔取几帧，拼成一张图 | L2 用它让一次视觉调用就能判断「这是什么」 |
| **EXIF** | 相机/手机写进照片文件的「拍摄说明书」：设备、时间、光圈、快门、ISO、GPS | 照片的拍摄日期和设备只能从这读，文件名和 mtime 都不可信 |
| **GPS / ISO6709** | 拍摄位置的经纬度。苹果把它写成 `+22.3681+113.6202+042.120/` 这种紧凑格式 | 索引里存成 `{lat, lon, alt_m}`，用来按地点找素材 |
| **光圈 / 快门 / ISO** | 进光量的三个旋钮：f 值越小进光越多（背景越虚）、快门越慢越容易糊、ISO 越高噪点越多 | 判素材上限：1/100·ISO 64 有宽容度，1/30·ISO 3200 已经到极限 |
| **主摄 / 超广角 / 长焦** | 一台手机上三颗不同的镜头。主摄视角接近人眼、画质最好；超广角拍得宽但边缘会变形；长焦拍得近、景深浅。iPhone 按焦距区分：<3.5mm 超广角、3.5–9.5mm 主摄、>9.5mm 长焦 | 同一段话一半主摄一半长焦，视角和景深会突然变，看着「跳」。库里标出哪颗镜头，才好在剪辑时避开这种拼接 |
| **Display P3 / sRGB** | 两种色域。P3 色域更宽（苹果屏幕默认），sRGB 是通用标准 | P3 照片直接当 sRGB 用会变灰，要先转 |

## 音频

| 术语 | 一句话释义 | 在 CutSkills 里意味着什么 |
|---|---|---|
| **LUFS** | 衡量「听起来多响」的单位，平台会把响度归一化 | 成片目标 −14 LUFS ±1；不达标会被平台压，动态全丢 |
| **dBTP / 真峰** | 换算回模拟信号后的峰值，数字峰值不超不代表真峰不超 | 上限 −1 dBTP，超了转 AAC/MP3 会削波爆音 |
| **ducking** | 有人说话时自动压低背景音乐 | 人声段落 −12dB，切换要 100–200ms 渐变，不要硬切 |
| **淡变 / fade** | 30ms 的音频淡入淡出 | 每个切点都要加，否则必有爆音 |
| **静音检测 / silencedetect** | 自动找出安静区间 | 用来判气口、判「这段是不是没人说话」 |

## 转写与索引

| 术语 | 一句话释义 | 在 CutSkills 里意味着什么 |
|---|---|---|
| **ASR** | 自动语音识别（Automatic Speech Recognition），把音频变成文字 | 用本地 `coli asr --model sensevoice`，离线、中文精确到字 |
| **字级 / 词级时间戳** | 每个字或词对应的时间区间，不是整句一个时间 | 切点吸附字界、字幕对齐都靠它；英文词级够用，中文要字级 |
| **同音误写** | 发音相同但写错的字，比如「石灰基」被写成「石灰机」 | 靠 `lexicon.json` 词表 + pypinyin 同音检测纠回来 |
| **语料 / corpus** | 一批可信的书面材料，用来确定「正确写法长什么样」 | 库里的品牌语料手册就是判定基准 |
| **L0 / L1 / L2** | 索引的三层深度：L0 技术指标、L1 全量转写、L2 画面内容判断 | L0 全量、L1 全量、L2 只跑候选段 |
| **must-use / backup / do-not-use** | 分级取用：必用 / 备用 / 不用 | 每级都带理由，不写理由的分级不算数 |
| **uid / 内容指纹** | 由文件内容算出的固定编号，改名搬家都不变 | 索引认人靠它，不靠文件名 |

## 剪辑

| 术语 | 一句话释义 | 在 CutSkills 里意味着什么 |
|---|---|---|
| **EDL** | 剪辑决定清单（Edit Decision List）：用哪条素材的哪一段、放在第几段、为什么 | `edl.json` 是唯一真值源，成片由它生成 |
| **纸面剪辑 / paper edit** | 先只用文字决定「留哪句、删哪句」，不碰时间线 | B 段的载体，人读 3 分钟就能确认 |
| **B-roll** | 覆盖在旁白/口播上的补充画面 | 声音走原口播、画面换素材，EDL 里用 `audio` 字段表达 |
| **padding / 切边留白** | 切点前后各留一点余量 | 30–200ms，吸收时间戳漂移；两段共用字界时要互相让位 |
| **J-cut / L-cut** | 声音先到 / 画面先走，让切换不突兀 | 口播片的常规手法，靠相邻段的时间重叠实现 |
| **镜头中位时长** | 所有镜头长度的中间值，衡量节奏 | 口播片 2.0–2.8s；长于这个数就是节奏拖 |

## CutSkills 自己的词

| 词 | 意思 |
|---|---|
| **A / B / C / D 段** | 索引 / 决定 / 成片 / 验收，按「人要不要介入」切 |
| **风格包 / style pack** | `styles/*.yaml`，字幕字号、镜头节奏、音效密度这些数字集中放一处 |
| **真值源** | 能被复算的那份数据；其余（paper-edit、pickup、报告）都是视图，可以删掉重建 |
| **意图 / intent** | 项目开头的四个字段：观众是谁、看完要相信什么、时长画幅、不许出现什么 |
| **论点 / beat** | 片子里一个独立的论证单元（「两种说法各摆一边」「我们怎么选」）。一条片子通常 3–5 个 | `plan.json` 里每段用 `beat: n` 归到某个论点；`check_edl` 按论点统计段数、时长、有没有证据 |
| **角色 / role** | 这一段在论证里干什么：`setup` 交代前提、`claim` 抛主张、`evidence` 给证据、`warrant` 说理、`turn` 转折、`payoff` 收束 | 只有 `claim` 没有 `evidence` 的论点，观众没有理由信——这是机器能查出来的论证缺口 |
| **说理 / warrant** | 证据和结论中间那半步：「为什么这条证据能推出这个结论」。借自论证学的 Toulmin 模型 | 观众不信的常常不是证据本身，而是这半步。机器判不了，盲测会指出来 |
| **盲测 / blind test** | 把片子稿交给一个不知道内情的人，只问三句：你想让我信什么、你拿什么当证据、哪里你不信 | B 段唯一的外部裁判。作者自评不算——写稿的那一方不许给自己打分 |
| **缺口清单 / gap.md** | 这条片子真的缺什么：论点缺证据或缺说理、用了库外素材、还差什么素材要人补 | 只列缺口，不列「可以更好」，否则清单会变成许愿池 |
| **试算 / dry-run** | 先按正式算法算一遍，但不落盘 | `preview_plan.py`：改一条计划就看得到时长、结构、语速，不用走完落盘那三步 |
| **入口检查 / intake** | 开工前先确认「这次是不是有明确需求的剪辑」 | `intake.py` 判 `full` / `thin` / `empty`；`thin` 时让用户在「给稿」和「我出选题」之间挑 |
